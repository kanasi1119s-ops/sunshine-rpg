# AI（言語モデル）に作曲ソフトで曲を作らせる手順書（2026-10-11 調査）

対象: Claude のような言語モデルが、うちの作曲ソフト（AIソング形式のJSON → MIDI／WAV）で曲を書くとき。
重複を避けるため、すでにある文書は読んだ前提にしている。ここでは「AI が作業する流れ」と「測って直す回路」に絞る。
- 他社の仕組みの比較 → `ai-music-tools-study.md`／コード進行 → `chord-variety-guide.md`／編曲 → `arrangement-guide.md`
- 楽器ごとの書き方 → `craft-guides.md`／ミックス → `mixing-guide.md`／本物らしさの測定 → `realism-roadmap.md`
- 形式そのものの説明 → `src/audio/ai-song.ts` の `AI_SONG_GUIDE`
※ 調べた文章は写さず、要点を自分の言葉でまとめた。論文の数字は各論文の自己評価で、うちの曲にそのまま当てはまるとは限らない。

---

## 1. 要点（先にこれだけ）

1. **音を作る AI と、楽譜を書く AI は別物。** 前者（Suno など）は完成品が一気に出るが、1音だけ直せない。後者（言語モデル＋MIDI／ABC／JSON）は、音の質は音源しだいだが、何度でも直せる。うちは後者で、強みは「直せること」。プロの現場でも、AI は技術作業（ミックス、マスタリング、編集）と下書き（アイデア出し）に多く使われ、核になる旋律と演奏は人が持つ、という使い分けが主流。
2. **一発で完成させない。** 研究でも現場でも、「最初の出力はそのまま使えない。直しながら育てる」が共通。言語モデルは1回の指示で長い曲を通して考えるのが苦手で、**小さな工程に割ると良くなる**（構成 → コード → 各パート → 点検）。
3. **構成（計画）を先に、文字として書かせる。** 曲全体の設計図（セクション・小節数・音の数・強さ）を先に決め、あとから細部を埋める方式は、構成の明快さと盛り上がりの評価が上がった（複数の研究）。人が設計図を直せる点も大きい。
4. **制約を数字で与える。** 調・テンポ・拍子・楽器・音域・小節数は、書いてあれば守られやすく、書いてなければ「ありがちな値」に寄る。「いい感じに」より「E♭ドリアン、bpm 98、旋律は C4〜G5」。
5. **繰り返しは設計する。** 言語モデルは、渡された動機をそのまま写す／同じリズムを続ける、になりやすい。動機を1つ決め、「何を変えるか（音域・リズム・音数）」を小節ごとに指定する。
6. **AI の自己採点は当てにならない。** 言語モデルに「この曲はよいか」と聞くと、正解率は偶然よりやや良い程度で、聞くたびにぶれる。**数字を出す道具（楽理チェック・ラウドネス・帯域）を判定役にして、言語モデルは直す役**に回す。最終判断は人の耳。
7. **点検は3段。** 譜面の段（音域・コードとの一致・単調さ）→ 音の段（ラウドネス・帯域・左右・ダイナミクス）→ 耳の段（ヘッドホンとスマホ、頭の10秒、サビの前後）。

## 2. 手順（作曲前 → 作曲中 → 書き出し後の点検）

### A. 作曲前（設計図づくり。ここで8割決まる）
1. **使い道を1行で言う。** 場面（町／戦闘／ボスなど）、感情の流れ、長さ（◯分◯秒）、ゲーム内での役目（くり返し再生されるか）。
2. **直前の曲を確認する。** `tracks.md` と `src/audio/songs/` の最近の曲を見て、調・bpm・進行レシピ・入り方・終わり方・主役の楽器が**かぶらない**ように選ぶ（似た曲ばかりになる最大の原因は、毎回同じ「いつもの選択」をすること）。
3. **属性カードを書く**（下の「プロンプトの型 1」）。調／旋法、bpm、拍子、進行レシピ（記号）、入り方（1〜8のどれか）、音域のすみ分け、サウンドセット。
4. **セクション表を書く。** セクション名・小節数・鳴るパート・強さ（1〜10）・「前と何を変えるか」。強さのカーブ（例: 2→4→6→9→3→10）を数字で。
5. **動機を決める。** 2〜4音（音名とリズムを明記）。育て方を3つ決める（高さをずらす／リズムを変える／後半を切る、など）。コード・旋律・伴奏の役割をパートごとに1行で書く。
6. **計画を人に見せられる形に残す。** description に、進行レシピ名・入り方・強さカーブを書く（あとで「同じ入り方が続いていないか」を調べられる）。

### B. 作曲中（書く → すぐ確かめる、を短い周期で）
1. **一度に全パートを書かず、核から。** ①コード進行とセクション表 → ②旋律 → ③ベースとドラム → ④和音の楽器・対旋律 → ⑤飾り（フィル・効果）の順。各段階で `node tools/composer/song.mjs build 曲.json`（WAV なしで速い）を回し、**エラーと「注意:」を読んでから次へ**。
2. **拍の勘定を毎小節確かめる。** 言語モデルは、音の長さの足し算（1小節＝拍子の拍数）をまちがえやすい。小節ごとに合計を書き出して数える／バーラインを意識して区切って書く。形式が小節をそろえて検査してくれるので、エラーが出たらその小節だけ直す。
3. **旋律はコードに合わせて点検する。** 拍の頭の音がコードの構成音か、ずれた音は経過音・倚音として「次で解決しているか」。音階外の音が出たら意図的か確認する。`score-check.mjs` に任せられる部分は任せる。
4. **変化を入れるのは「1回に1つ」。** 2回目の同じ進行で、足す／変える物を1つ指定して書く（全部変えるとまとまりが消える）。
5. **人間らしさは後から、ただし書き方の段階で仕込む。** 強拍と弱拍の強さ差、ゴーストノート、フレーズ末の引き、ベロシティの散らばり、わずかな前ノリ・後ノリ。ドラムの全パートを同じ量で揺らさない（キックとスネアは安定、ハイハットは大きく揺らす）。ミックスの前に、`human` と `dynamics: "natural"` を使う。
6. **パートを1つずつ消して聴く。** 消しても成り立つパートは要らない。足すより先に引く。

### C. 書き出し後の点検（数字 → 耳）
1. **楽理チェック**: `node tools/audio-check/score-check.mjs 曲.json`（音域、コードとの一致、旋律の単調さなど）。
2. **WAV を作る**: `node tools/composer/song.mjs build 曲.json --wav`。ここで出る「音割れ」「低音の多すぎ」「強弱の幅」「途中の無音」の注意を読む。
3. **音の数字**: `python3 tools/audio-check/analyze.py 曲.wav`／`--compare`／`--bands`、`realism.py`。見る数字と目安:
   | 見るもの | 目安 | 外れたときの直し方 |
   |---|---|---|
   | 統合ラウドネス（LUFS） | 配信の基準は -14 前後（Apple は -16）。ゲームは `bgm-loudness.json` で曲どうしをそろえる | volume の合計を調整。リミッターだけで稼がない |
   | 真のピーク（dBTP） | -1 以下（圧縮して配信すると山が上がるため） | 全体の音量を下げる、歪みギターの volume を下げる |
   | ラウドネスレンジ（LRA） | 市販のロックやポップで 4〜8 LU。1以下は平ら | セクション表の強さ差を広げる、`dynamics: "natural"`、サビ前の引き |
   | PLR（ピーク−ラウドネス） | 9未満は潰れ気味 | 圧縮を浅く、パートの足しすぎをやめる |
   | 帯域（sub／bass／lowmid…） | `--bands` の診断に従う | 濁り＝200〜500Hz の重なり、刺さり＝2〜5kHz。音域をずらす／volume を下げる |
   | 左右の相関 | 0.4〜0.88 ほど | 和音の楽器を左右に、低音とリードは中央 |
   | 出だしのずれ（timing_ms） | 5ms より小さいと機械的 | `human` を足す |
4. **基準の曲と比べる（数字だけ）。** 比べる前に、音量（LUFS）を±0.5 dB ほどにそろえる（小さい方が低音や高域が弱く聞こえる錯覚を避けるため）。既存の録音の数字は `docs/sound/data/` にある。曲を真似るためではなく、**帯域・ダイナミクスの偏りを見つけるため**に使う。
5. **耳**: ①頭の10秒で前の曲と区別がつくか ②サビが Aメロより大きく高いか ③切り替わりに「間」があるか ④ヘッドホンとスマホの小さいスピーカーの両方 ⑤1曲を通して聴いて、**飽きる場所**に印をつける。数字が良くても違和感があれば耳を優先する。
6. **直しは1回に1点。** 直したら同じ測定をもう一度回し、数字の変化と耳の印象を `docs/sound/tracks.md` の曲の備考に残す（何をどう直して何が変わったか）。

## 3. プロンプトの型の例

### 型1: 属性カード（作曲前に必ず埋める。書かない項目は「ありがちな値」になる）
```
曲名／場面: （例）雪原の夜のフィールド曲。静かな孤独から、遠くに灯りが見える希望へ
長さ: 2分30秒前後（くり返し再生される）
調・旋法: （例）D ドリア。サビ前だけ B♭ に借用
bpm・拍子: 92／4拍子（swing 0.2）
進行レシピ: chord-variety-guide の（記号）。直前の3曲と違うことを確認済み
入り方: （1〜8のどれか。直前の曲と違うもの）／終わり方: （毎回変える）
音域のすみ分け: ベース E1〜G3、和音 C3〜C5、旋律 C4〜G5（かぶらない）
サウンドセット／ジャンルの手がかり: （`song.mjs sounds` の中から）
使わない音: banned-sounds.md を確認済み
```

### 型2: セクション表（強さカーブと「前との違い」）
```
| セクション | 小節 | 鳴るパート | 強さ | 前との違い |
| 導入 | 4 | pad, bell | 2 | （最初）旋律なし、ドローンだけ |
| Aメロ | 8 | + bass, melody | 4 | 旋律が入る、ドラムなし |
| Bメロ | 4 | + strings | 6 | 音域を上げる、進行を変える |
| サビ | 8 | 全部 | 9 | 動機を高く、長い音で |
| 間奏 | 4 | 1〜2パート | 3 | 全員止めてから入る |
| 最後のサビ | 8 | 全部+対旋律 | 10 | 半音上に転調、または1拍止めてから |
```

### 型3: 小さな工程に割る指示（一度に頼まない）
1. 「型1と型2だけを書く。音符はまだ書かない。」→ 人（または検査役）が見て直す。
2. 「コード進行を、型2の小節数に合わせて書く。借用和音・7th などを入れる場所に印を付ける。」
3. 「動機を音名とリズムで書き、Aメロ4小節だけ旋律を書く。コードの構成音との関係を小節ごとに一言ずつ添える。」→ `build` で確認。
4. 「残りのセクションの旋律を、動機の変形で書く。各セクションで何を変えたかを一行で。」
5. 「ベース → ドラム → 和音の楽器。セクション表の強さに合わせる。」
6. 「`build` の注意と `score-check` の警告を貼る。**1つずつ**直す案を出し、直す前と後を比べる。」

### 型4: 直すとき（測定の数字を渡して、直し方を1点に絞らせる）
```
測定: LRA 0.9 LU、PLR 8.4、200〜500Hz が基準より +3dB、頭が最大音量と同じ。
目的は「サビ前に静けさを作る」ことだけ。次の3点以外は触らない:
 (1) Bメロの最後の1小節でドラム以外を R にする
 (2) 弦の音域を C3〜C4 から C4〜C5 に上げる（濁り対策）
 (3) 導入の volume を 60% にする
直したあと、変えた箇所の一覧を出し、再測定の見るべき数字を3つ書く。
```

### 型5: 独立した点検役（別の役割で読ませる）
「いま書いた曲を、作者ではなく校正係として読む。①音域外 ②拍の合計ちがい ③コードに合わない拍頭の音 ④同じ4小節が3回以上 ⑤直前の曲と同じ入り方、をそれぞれ小節番号つきで列挙する。感想は書かない。」
（言語モデルの「よい曲です」は信用しない。**小節番号つきの事実の列挙**だけを使う。）

## 4. 失敗と対策

| 失敗 | 起きる理由（調査から） | 対策 |
|---|---|---|
| 毎回似た曲になる（同じ調・同じ4コード・同じ入り方） | 出力が学習データの「ありがちな形」に寄る。ABC 形式の出力が民謡風に偏ったという報告もある。属性を書かないと平均に寄る | 作曲前に直前の曲と照合し、調・進行レシピ・入り方・終わり方を**先に違うものを指名**する。`chord-variety.mjs` の警告を守る |
| 単調（リズムが同じ、音量が平ら） | 指示に忠実でも、リズムが単純な反復になりやすい（研究で報告） | セクションごとに「リズムの型」を変える指示、強さカーブ、`dynamics: "natural"`、`human`。LRA を数字で確認 |
| 拍の数え間違い、小節がずれる | 長さの足し算が苦手。複数パートの小節の位置がずれると不協和になる（複数パートの小節をそろえる記法の研究がある） | 小節ごとに合計拍を書き出す。`build` のエラーで直す。大きな曲は4〜8小節ずつ書く |
| コードと旋律が合わない、音階外の音 | 「音が正しい形式で出る」ことと「音楽として意味がある」ことは別。動機を写すだけで意味を扱えていない例が報告されている | 拍頭＝コード構成音の原則を書かせ、小節ごとに説明を添える。`score-check` と、別役割の校正係 |
| 音域のぶつかり・低音の濁り | パートごとに別々に書くため、重なりに気づかない | 作曲前に音域表を決める。`build` の「音域が重なっています」を必ず読む。片方を3度〜1オクターブずらす |
| 動機を写すだけで育たない | 指示が「動機を使って」だけだと、そのまま反復する | 「何を変えるか」（高さ・リズム・長さ・向き）を小節単位で指定する |
| 始まりと終わりが唐突 | 生成物は始まり・終わりの設計が弱いという報告 | 入り方（1〜8）と終わり方を属性カードに書く。ゲームの曲はくり返すので、最後→最初のつなぎも決める |
| 音の質感を文章で頼む（「ざらついたシンセ」など） | MIDI は楽譜であって音色の情報を持てない | 質感は音色（patch）・アンプ・サウンドセット・ミックス欄で指定。言葉でなく設定値で頼む |
| 機械的なのに、全部を揺らして雑になる | 全パートを同じ量でランダムにするとだらしなく聞こえる | キックとスネアは安定、ハイハットとゴーストを揺らす。フレーズごとに強さの山を作る。ソロで判断せず、全パートで聴く |
| 数字だけ整えて平板になる | 音量を稼ぐ圧縮で強弱が消える | 圧縮は 1〜3 dB 程度の浅さを目安。LUFS を目標にして潰さない |
| AI の自己評価で「完成」と判断してしまう | 判定がぶれ、言い回しに左右される | 数字と、小節番号つきの事実の列挙を判定役にする。判定は同じ入力で2回出して一致するものだけ採用 |
| 聴いて直してもまた同じ失敗 | 修正が記録されない | 直しの理由と結果を `tracks.md` の備考に1行残す。同じ失敗が3回出たら、この文書か `AI_SONG_GUIDE` に決まりとして追記 |

## 5. うちの作曲ソフトの機能との対応表

| 工程 | 研究・現場で効くこと | うちの機能・文書 | 状態／ほしいもの |
|---|---|---|---|
| 設計図を先に | 構成を先に決めてから細部（階層的な作り方） | `AI_SONG_GUIDE` の編曲家の項、`sections`、`arrangement-guide.md` | 設計図の**ファイル化と検査**がない（提案1） |
| 属性の明示 | 調・テンポ・拍子・楽器を書く | JSON の bpm／beats／chords／parts、`song.mjs sounds` | 属性カードの雛形がない（提案1） |
| 曲の重なりを避ける | 直前の曲との差 | `chord-variety.mjs`、`tracks.md` | 入り方・終わり方・調の重複検査がない（提案2） |
| 部分的に作って確かめる | 小さな工程＋検証ループ（規則による検査器で誤りを返す方式が効く） | `song.mjs build`、`score-check.mjs`、`song-check.ts` | 周期的な自動実行の流れがない（提案3） |
| 人間らしさ | ベロシティ・タイミングの揺らぎ、ゴーストノート | `human`、`dynamics: "natural"`、奏法記号、`drum-fills.md` | パートごとの揺らぎ量の推奨値の表（提案6） |
| ラウドネス | LUFS／真のピーク／LRA | `analyze.py`、`realism.py`、`loudness.ts`、`bgm-loudness.json` | 目安を一枚にした合否表（提案4） |
| 帯域・左右 | 基準曲との比較（音量をそろえてから） | `analyze.py --bands --compare`、`third-octave.py` | 曲ごとの結果の記録先がない（提案5） |
| 直しの記録 | 反復して育てる | `tracks.md` の備考 | 形式が決まっていない（提案7） |
| 別役割の点検 | 自己採点は不安定 | `score-check.mjs` | 「校正係」の出力形式の固定（提案8） |
| 外部のDAWとの連携 | MCP で DAW のクリップを読み書きする例がある | `tools/mcp/server.mjs`（compose_song など） | 当面は不要。MIDI 書き出しで足りる |

## 6. 取り入れる提案（実装できる大きさに分けた）

1. **「曲の設計図」ファイル（`<曲>.plan.json`）と検査**: 属性カード（調・旋法・bpm・拍子・進行レシピ・入り方・終わり方・音域表）とセクション表（小節・パート・強さ・前との違い）を JSON にし、`song.mjs plan-check` で「小節の合計が曲の長さと合うか」「パートが音域表を守っているか」「強さカーブに山があるか」を検査。完成した曲の JSON との食い違い（計画にないパートが鳴る等）も警告。
2. **新しい曲の重複検査 `song.mjs novelty`**: `tracks.md` と `songs/` の最近 N 曲を読み、調・bpm・進行レシピ・入り方・終わり方・主役の楽器が直前の曲と同じなら警告。`chord-variety.mjs` の拡張として作る。
3. **段階ビルドの手順を `compose-song` に追記**: 「設計図 → 進行 → 旋律 → ベース・ドラム → 和音 → 飾り」の各段階で `build` を回し、エラーと注意を次の指示に貼る、という固定の流れを手順書にする（コードは不要。文書の追加）。
4. **合否表 `song.mjs gate`**: 書き出した WAV に対して、LUFS・真のピーク・LRA・PLR・相関・頭の音量・途中の無音を一度に測り、目安（本書 C-3 の表）と比べて「○／要直し」を日本語で出す。既存の `analyze.py` と `realism.py` を呼ぶだけの薄い包み。
5. **測定結果の保存 `docs/sound/data/ours/<曲ID>.json`**: 数字だけ（曲の音は入れない）を保存し、過去の曲との比較・推移を見られるようにする。基準曲との LUFS をそろえる処理も含める。
6. **揺らぎ量の推奨値の表**: パート別（キック／スネア／ハイハット／ベース／和音／旋律）の `human` の効き方の目安を実験で決め、`craft-guides.md` の15に表として追加。ハイハットは大きく、キックとスネアは小さく、を数字にする。
7. **直しの記録欄の定型化**: `tracks.md` の備考に「直す前の数字 → 直した点（1つ）→ 直した後の数字 → 耳の印象」を1行で書く形式を決め、書き忘れを `build` の終わりに表示して促す。
8. **校正係の出力形式の固定**: `score-check.mjs` の出力を、「小節番号／パート／種類（音域外・拍の合計・拍頭の不一致・同じ4小節の反復・入り方の重複）」の表形式（JSON も）で出せるようにし、言語モデルが「感想」でなく「事実の列挙」を読んで直せるようにする。
9. **動機の台帳 `motifs` 欄（任意）**: 曲の description に動機（音名とリズム）と変形の履歴を書く欄を決め、`score-check` が「動機が各セクションで現れているか」「同一のまま反復していないか」を数える。
10. **曲どうしの「差」の点数化**: 最近 N 曲の旋律の輪郭（Parsons code。すでに `PARSONS=1` で出せる）と進行の形の類似度を数字にして、似すぎた曲を作り直す基準にする（旋律をそのまま再利用しない確認にも使える。既存作品との照合は行わない）。

優先順位の案: 4 → 1 → 2 → 8 → 7 → 3 → 5 → 6 → 9 → 10。

## 8. 実装状況（2026-10-11）

6節の提案10個のうち、9個を入れた。コマンドは `node tools/composer/song.mjs <名前>`（vite を起動しない軽い処理）。

| 提案 | 状態 | 入れたもの・場所 |
|---|---|---|
| 1 設計図ファイルと検査 | 入れた | `plan-template`（雛形）・`plan-check <plan.json> [曲.json]`（`tools/composer/plan-check.mjs`）。属性カード（調・旋法・bpm・拍子・進行レシピ・入り方・終わり方・音域表）とセクション表（小節・パート・強さ・前との違い）。検査: 未記入の項目／強さカーブの山（差4以上・山7以上・最初が山でないか・同じ強さが3つ続かないか）／「前との違い」の空欄／音域表のかぶり／曲を渡すと、小節の合計・bpm・拍子・調・音域表と実際の音域・計画にないパートが鳴っていないか |
| 2 新しさの検査 | 入れた | `novelty <曲.json> [--n 3] [--vs 曲名,曲名]`（`novelty.mjs`）。調（主音と長短）・テンポ（±4）・進行の形（回して書いても同じ）・入り方・終わり方・旋律の楽器を、`assets-src/ai-songs/` の更新が新しい N 曲と比べる。`build` の「注意:」にも自動で出る。**入り方・終わり方は description か plan に「入り方: 5」「終わり方: 余韻を残して消える」と書くとそのとおりに数え、書かなければ最初の小節の鳴り方から推測する**（推測できるのは 1・2・4・5・6・8）。`tracks.md` は自由な文章なので読まない |
| 3 段階ビルドの手順 | 入れた | `.claude/skills/compose-song/SKILL.md` に追記（文書のみ） |
| 4 合否表 `gate` | 入れた | `gate <曲.wav> [--target -14] [--save 曲ID] [--json]`（`gate.mjs`）。ffmpeg の ebur128 で LUFS・真のピーク・LRA・PLR、WAV から左右の相関、頭の大きさ（最初の10秒−曲の最大の短時間ラウドネス）、途中の無音（4秒以上）を一度に測り、C-3 の表の目安と比べて「○／要直し」と直し方を日本語で出す。要直しがあると終了コード2。**`analyze.py`／`realism.py` は呼んでいない**（Python と numpy なしで動くよう ffmpeg だけにした）。出だしのずれ（timing_ms）と帯域診断は従来どおりそちらで測る |
| 5 測定結果の保存 | 入れた | `gate --save 曲ID` で `docs/sound/data/ours/<曲ID>.json` に数字だけを追記（履歴つき。前回との差を表示）。`gate-compare 曲.wav 基準.wav` は、基準の LUFS に曲の音量をそろえてから、sub／bass／lowmid／mid／highmid／high の6帯域の差を出す |
| 6 揺らぎ量の推奨値の表 | **入れていない** | 実験（書き出した音を聴いて決める）が要るため。いまの `human` は曲全体に1つの値で、パート別に効かせる仕組みもないので、表だけ書いても使えない |
| 7 直しの記録の定型化 | 入れた | `log <曲ID> --before .. --change .. --after .. --ear ..` で `docs/sound/revisions.md` に「日付 曲ID: 直す前 → 直した点 → 直した後 → 耳」を1行追記。`build` の終わりに、記録がない曲へ促しを表示。**書き先は提案の `tracks.md` でなく新しいファイル**にした（`tracks.md` は他の作業と同時に編集されやすく、マージで衝突するため） |
| 8 校正係の出力形式 | 入れた | `score-check.mjs <曲.json> --facts`（表）／`--json`。「小節／パート／種類／内容」。種類は 音域外・拍の合計・拍頭の不一致・アヴォイドノート・同じ4小節の反復・動機・入り方の重複。従来の出力（○△の一覧）は変えず、既定の出力にはアヴォイドノートの件数を1行足した |
| 9 動機の台帳 | 入れた（簡易） | description に「動機: E4:1 G4:1 A4:2」と書く（または plan.json の `motif.notes`）。`--facts` が、動機の音程の並びが旋律に出ない／セクション（`sections` か plan のセクション表）に現れない／高さもリズムも同じまま4回以上出る、を知らせる。変形の履歴の記録欄は作っていない |
| 10 曲どうしの差の点数 | 入れた | `novelty` が、旋律の輪郭（Parsons code の8音ぶん）の重なりと進行の一致から「差の点数」（100に近いほど違う）を出し、輪郭が35%以上重なると警告。**自作の曲どうしの比較だけ**（既存作品との照合は行わない） |

追加で直したこと
- `score-check.mjs` は、長さに奏法の記号が付いた音（`E5:1!` など）を読み飛ばしていた。共通部品 `tools/audio-check/score-lib.mjs` で読めるようにし、分数コード・6・9・m7b5 も和音として読む。
- `Am*2`・`sectionChords`・`modulate`・`loopTail` を使う曲も、ゲームと同じ前処理（`src/audio/song-plan.ts`）をかけてから点検する。
