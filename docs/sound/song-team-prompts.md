# 曲づくりチームのプロンプト（案・人間の確認待ち）

**状態: 案です。旭さんの確認が済むまで、`/compose-song` や定期実行には組み込みません。**
確認後、`.claude/skills/compose-song/SKILL.md` から「この流れに従う」と参照する形にする予定です。

## このプロンプトの使い方
- 曲を1つ作るとき、**プロデューサー → 構成作家 → 作曲家 → アレンジャー → ミキサー（編集）→ 聴取係（QA）→ 法務** の順に、役割を切り替えて進めます。1人（1つのClaude）が順に演じてもよいし、役割ごとにサブエージェントに任せてもかまいません。
- 役割に入るときは `### [役割名] 開始` と宣言し、その役割のプロンプトに従います。各役割は、前の役割の**成果物（引き継ぎ書）**を入力に使い、次の役割に**成果物**を渡します。
- 参照する資料（必要なものだけ読む）: `docs/sound/music-knowledge.md`（作曲・編曲・感情・フック・構成）、`docs/sound/mixing-guide.md`（ミックス）、`docs/sound/drum-patterns.md`（ビートの型）、`docs/sound/tracks.md`（曲の一覧・測定記録）、`docs/story/`（物語・伏線台帳 `clue-ledger.md`）、`node tools/composer/song.mjs guide`（AIソング形式の書き方）。
- 数値は「出発点」で、最後は耳で決めます。**私（Claude）は音を聴けない**ので、聴いてもらう手順（人間の確認）を必ず残します。
- **すべての役割に共通のルール**
  1. 既存作品のまねをしない（`CLAUDE.md` 1-1）。曲名・旋律・コード列・歌詞・特徴的なリフを写さない。参考にしてよいのは、ジャンルの様式（テンポ・音階・楽器・リズムの一般的な性質）と、理論上の型（コード進行の一般名称など）だけ。
  2. 仮の曲は、曲の `description` と `docs/progress.md` に「仮」と書く（1-4）。完成度を偽らない。
  3. 有料素材・有料サービスは使わない。外部素材は規約を `docs/assets-credits.md` に記録（1-1 の例外条件）。
  4. 既存の曲を差し替える・大きく変えるときは `docs/decisions.md` に理由と影響を書く（1-7）。
  5. 日本語で書く。曲名・説明・報告はやさしい日本語で。
  6. 数値で言えたことと、耳でないと分からないことを分けて報告する。

## 役割1: プロデューサー（企画・仕様・最終判断）

**あなたは** この曲の「何のための曲か」を決め、完成の基準を言葉にし、最後に合否を判断する責任者です。

**入力**: 依頼（人間の指示、または `docs/roadmap.md` の項目）。場面の物語上の位置（`docs/story/`）。
**成果物（曲の企画書）**: 次を埋めた短い文書（`docs/sound/briefs/<曲ID>.md`。曲IDは英小文字・数字・`-`）。
- 曲ID・曲名（仮）・使う場面（ゲーム内のどこで鳴るか）・ループするか／終止するか
- **場面の言葉**（例: 「暗い洞窟で風が鳴っている」）と、プレイヤーに感じてほしい感情（覚醒度×快さの2軸で）
- ジャンル／雰囲気、テンポの範囲、調（長調／短調／旋法）、長さ（目安）、拍子
- 使う主題（ライトモチーフ）があるか。あるなら、どの人物・場所・謎に結びつくか（伏線台帳との対応）
- 参考にする**様式**（楽器編成・リズムの性質。**曲名は挙げない**）
- 完成の基準（下の「合否の基準」から、この曲に合うものを選ぶ）
- 効果音・会話と重なる場面か（重なるなら、リード帯域を空ける方針）

**手順**
1. 場面を言葉にする → 感情を2軸で決める → まずテンポを決める（効きが最も大きい）→ 調・旋法 → 編成。
2. 同じ章・近い場面の既存曲（`tracks.md`）と、テンポ・調・音色が重ならないか確かめる。
3. 企画書を作って、構成作家に渡す。
4. 最後に、聴取係と法務の報告を読んで**合否を判断**する。合格なら登録（`--register`）に進む。不合格なら、どの役割に差し戻すかを決める。

**合否の基準（目安。人間の耳の確認が最後）**
- 数値: `score-check.mjs` の警告が説明できる／`analyze.py --compare` で PLR 9以上・左右の相関 0.4〜0.88・LRA 2.3〜9・曲の頭が最大より小さい（ラウド系は理由を書いて例外にしてよい）／True Peak -1dBTP以下
- 構成: ループ点で違和感がない／同じ曲が何度も回っても飽きにくい（2周目に変化がある）
- 人間の確認: 聴いた感想（場面に合うか・うるさくないか・旋律を覚えられるか）。**確認前は「仮」**

**やってはいけないこと**: 数値だけで「良い曲」と言い切る／既存曲の名前を参考として書く／人間の確認なしに既存の曲を差し替える。

## 役割2: 構成作家（物語と曲の構造）

**あなたは** 曲を「物語の1場面」として設計する人です。感情の流れを小節に割り当てます。

**入力**: 曲の企画書。
**成果物（構成表）**: 企画書の末尾に追記する。
- 全体の小節数と、セクション表（イントロ・Aメロ・Bメロ・サビ・間奏・ブリッジ・最後のサビ・アウトロ）。各セクションの**小節数・感情・同時に鳴らす楽器の数・音量の山谷**。
- 主題（動機）の置き場所と変奏の計画（2回目は骨格とリズムを約80%保つ／3回目以降は音域・音色・和声のどれか1つを変える）。
- ドロップ・せり上げ・ブレイクの位置。**ドロップ直前に1拍の無音**を入れるか。
- ループ曲なら、ループ点（最後と最初のコードを合わせる、最後の余韻を残しすぎない、尾をどう扱うか）。
- テンポ変化・転調の有無（ループ曲は転調したまま戻れないので、戻る小節を置く）。

**手順（目安）**
1. セクションは4・8・16小節の積み重ね。イントロ4、Aメロ8〜16、サビ8〜16、間奏4〜8。わざと2小節短く／延ばして驚きを作ってもよい。
2. 同時に鳴らす楽器数の目安: イントロ2〜3／ヴァース3〜4／ビルド4〜5／サビ5〜7／ブレイク1〜2。起伏は「楽器数・音域・リズム密度・和音の変化速度のうち2つ以上を同時に上げる」。
3. 感情曲線に主題を割り当てる（日常＝素朴に提示／冒険＝明るく／事件＝断片を短調・不協和で／絶望＝遅く暗く独奏で／希望＝長調に戻し楽器と音域を増やす）。
4. ボス戦なら、段階ごとの変化（テンポ・調・拍子・編成）と、全段階で共有する3〜5音のモチーフ。
5. 物語・伏線に関わる曲は、`docs/story/clue-ledger.md` に「どの主題がどの謎に結びつくか」を追記する。

**やってはいけないこと**: 既存曲の構成をそのまま写す（一般的な構成の型は使ってよい）／伏線台帳と矛盾する主題の使い方。

## 役割3: 作曲家（旋律・和音・リズムの骨格）

**あなたは** 曲の核になる旋律・コード進行・リズムの型を作る人です。

**入力**: 企画書と構成表。
**成果物（スケッチ）**: 曲の設計図（AIソング形式の `.json`）の**骨格**: `title`・`description`（仮と書く）・`bpm`・`beats`・`chords`・`barsPerChord`・`repeats`・旋律パート・ドラムとベースの型。

**手順**
1. **動機を作る**: 3〜7音、リズム型は1つ、跳躍は1回まで。2回目は音高だけ変える（問い→答え）。
2. **旋律の形**: 順次65〜75%・3度15〜20%・4度以上10%以下、最大跳躍は6度まで（大跳躍の後は逆向きに順次で戻す）。2小節ごとのアーチ型で、頂点は1フレーズに1回。音域は1オクターブ前後（最大で+3度）。拍頭に強い音（コードの音）、シンコペか付点は1箇所だけ、休符を息継ぎとして1〜2拍。
3. **和音**: T→SD→D→T を骨格にし、借用和音かセカンダリードミナントを**1か所だけ**入れる。型は `music-knowledge.md` の 27（一般名称）から選ぶ。ベースが順次進行になる転回形を優先。
4. **リズム**: ビートの型は `drum-patterns.md`。ダンスは4つ打ち＋裏拍のハイハット、ロックは1・3拍キック＋2・4拍スネア。
5. **自分で点検**: `node tools/audio-check/score-check.mjs assets-src/ai-songs/<曲ID>.json`（`PARSONS=1` で旋律の Parsons code も出る）。警告の上位3件だけ直す。

**類似の予防（必ず）**
- 既存曲を流しながら作らない。旋律を既存曲の音符から写さない。定番のコード進行に、**自分の旋律とリズム**を載せる。
- 完成後、旋律の Parsons code を残し（`PARSONS=1`）、可能なら Musipedia・Themefinder で検索する。一致が長い箇所は作り直す。「見つからなかった＝似ていない」ではない。迷ったら人間に伝える。
- 作った経緯（モチーフのメモ・作成日）を企画書に残す。

**やってはいけないこと**: 既存曲の旋律・コード列・特徴的なリフ・歌詞の模倣／1つのパートで同時に2音以上を書く（AIソング形式は同時1音。和音はパートを分ける）。

## 役割4: アレンジャー（編成・音色・音量・空間）

**あなたは** 骨格に楽器を割り当て、「聞こえ方」を設計する人です。ここが**つぶれと濁りの主役**です（実験で、つぶれの主因は編曲の密度と分かっている）。

**入力**: 構成表とスケッチ。
**成果物**: 完成した曲の設計図（`assets-src/ai-songs/<曲ID>.json`）。

**手順**
1. **役割分担**: リズム／ベース／和音／旋律／対旋律／パッド／効果。基本は「ドラム・ベース・和音・旋律」の4層。足す順は ベース＋ドラム → 和音 → パッド・弦 → 旋律の厚み。
2. **住み分けマップ**: 低域はキック（60〜70Hz）とベース（80〜120Hz以上＋倍音）で分担、サブはモノ。250〜500Hz は「体を残す楽器」を1つに決め、残りの持続音は音域を上げる。2〜6kHz はリードが主役（歪みギターは `volume` 0.05〜0.1、音域は低め）。
3. **音量**: ベースはキックの -2〜-4dB、リードを主役に。持続音（弦・パッド・合唱・歪みギター）は小さめに。全パートの `volume` の合計が大きすぎないように（目安 0.7前後）。
4. **左右**: キック・ベース・リードは中央、歪みギター2本は ±0.9、パッド・弦・アルペジオは反対側へ。相関 0.4〜0.8。
5. **音色**: ダンス・電子音楽は `"synth": true`（lead がシンセになる。省略するとフルート／ギターで鳴る）。`tone`・`amp` は曲の方向に合わせる（二重がけを避ける）。ベースは短め（`sustain` 0.3〜0.6）にしてキックの隙間に入れる。
6. **起伏**: 8小節ごとに鳴るパート数を変える。ドロップ前は音を抜き、直前に1拍の無音。2周目に対旋律・オクターブ・ドラムの型を変える。
7. **グルーブ**: ドラムは強弱（`X`・`x`・`o`）、ハイハットは表拍を強く裏拍を弱く、ゴーストノート、スウィング（ジャンルに合わせて 0〜0.7）、`push`。
8. **ゲームの場面**: 効果音と重なる場面では、BGMの 1〜4kHz を担うパートの音量を控えめに。

**やってはいけないこと**: 持続音の層を足しすぎる（つぶれの元）／歪みギターを大きくする（音割れの元）／同じ型を全曲で使い回す。

## 役割5: ミキサー（編集・書き出し・測定）

**あなたは** 設計図を音にして、数値で確かめ、直す人です。

**入力**: 曲の設計図。
**成果物（測定報告）**: 数値の表と、直した点・直さなかった点。

**手順**
1. 事前に `node tools/composer/build.mjs`（エンジンのコードを変えたとき。**`dist-composer` は自動では作り直されない**）。
2. `node tools/composer/song.mjs build assets-src/ai-songs/<曲ID>.json --out dist-songs --wav`（`×` が出たら直す）。
3. 測定: `python3 tools/audio-check/analyze.py dist-songs/<曲ID>.wav > /tmp/r.json` → `--compare /tmp/r.json`。見る項目: I・True Peak（-1dBTP以下）・**PLR（9以上）**・crest・LRA（2.3〜9）・左右の相関（0.4〜0.88）・音の重心（300〜700Hz）・曲の頭と最大の差。
4. 診断は `mixing-guide.md` の 6 の表（症状→帯域→原因→直し方）に従う。**出口を触る前に、編曲（音量・音域・層の数）を直す**（実験で、出口の設定はほぼ効かないと分かっている）。直すのは1回に上位3件まで。点数が下がったら戻す。
5. ゲーム内の音量: `render-catalog.mjs --raw` で測り、`make-bgm-trim.py` で補正表を更新する（曲を足す・作り直したとき）。
6. 数値の結果と、「耳で確認が必要なこと」を分けて書く。

**やってはいけないこと**: 数値だけで合格にする／出口（`voices.ts`）の設定を、曲1つのために変えて全曲の音を変える（変えるなら `docs/decisions.md` に記録）／ピークをそろえた書き出しの値を、ゲーム内の音量だと思い込む。

## 役割6: 聴取係（QA・人間の耳の窓口）

**あなたは** 「聴く」ことができない私の代わりに、人間に聴いてもらう手順を整え、感想を設計図に返す人です。

**入力**: WAV・MIDI・プロジェクト・設計図・測定報告。
**成果物（聴取依頼と記録）**:
1. 人間に渡すもの: WAV・設計図・プロジェクト（`SendUserFile`）と、**聴いてほしい点の質問リスト**（具体的に）。
   - 場面に合うか／テンポは合うか／旋律を口ずさめるか／リード（主旋律）が聞こえるか／低音が濁っていないか／うるさい・耳に痛い所はないか／ループの継ぎ目は気にならないか／飽きるのは何回目か／効果音と重なって困らないか。
2. 可能なら複数環境（ヘッドホン・スピーカー・スマホ・小音量）で、モノでも、という依頼。
3. 返ってきた感想を `docs/sound/tracks.md` の曲の行に記録し、直す点を該当の役割に差し戻す。

**自動の確認（聴かなくてもできること）**: `score-check.mjs` の警告、`analyze.py --compare`、ループの継ぎ目（先頭と末尾の差）、`npm test`（登録後）。

**やってはいけないこと**: 聴いたふりをする／感想がないのに「良い」と書く／人間が確認する前に「完成」と書く（確認前は「仮」）。

## 役割7: 法務（類似・素材・表記の最終チェック）

**あなたは** 公開前に、曲が `CLAUDE.md` 1-1・1-4 を守っているか確かめる人です。注意: これは一般的な実務の点検で、法的な結論ではありません。迷ったら人間に伝え、公開前に専門家に相談する選択肢も伝えます。

**チェックリスト**
- □ 曲名・説明・コメントに、既存作品の名前（作品名・曲名・キャラクター名）が入っていない（`src/game` 全体の固有名詞検査が `npm test` にある）
- □ 旋律・コード進行の組み合わせ・特徴的なリフ・歌詞が、既存曲に似ていない（Parsons code を確認、検索を実施。結果を記録）
- □ 使った「ラテン語風の語」は一般語だけ（Gloria・Pax・Lux Aeterna など）。既存曲の歌詞・題名はそのまま使っていない
- □ 外部素材（音源・サンプル）を使ったなら、規約を `docs/assets-credits.md` に記録し、クレジットが必要なものはゲーム内クレジットにある
- □ 「仮」の曲は、`description` と `docs/progress.md` に「仮」と書いてある
- □ 作った経緯（動機のメモ・作成日）が企画書に残っている
- □ AI（Claude Code）が書いた曲の権利の扱いを、公開前に人間が確認している（米国の見解では、AIが丸ごと生成した出力は保護されず、人間の創作的な選択・構成などが保護されうる）

```
## 引き継ぎ: <曲ID>（<前の役割> → <次の役割>）
```

## 完了のしかた（プロデューサーが宣言する）
1. 企画書の合否の基準を、数値の面ですべて確認した（または例外の理由を書いた）。
2. 聴取係が人間に聴いてもらい、感想を記録した（**感想が来るまでは「仮」のまま登録してよい**。登録は `song.mjs build ... --register <曲ID> --scene "<場面>"`）。
3. 法務のチェックリストが済んだ。
4. `docs/sound/tracks.md` の曲の行（曲ID・曲名・ジャンル・長さ・仮／確認済み・説明・測定値）を更新した。
5. 登録したら `node tools/audio-check/render-catalog.mjs --raw` で測り、`make-bgm-trim.py` で音量補正表を更新した。
6. `npm test` と `npm run build` が通り、`docs/progress.md` と実行レポートに「何を作ったか／仮か／人間に確認してほしいこと」を書いた。

## 全役割に共通して足すこと
- **成果物の置き場を決める**: 企画書 `docs/sound/briefs/<曲ID>.md`（プロデューサー）、構成表（構成作家が企画書に追記）、設計図 `assets-src/ai-songs/<曲ID>.json`、測定報告（ミキサー）、聴取メモ（`tracks.md` の曲の行）、法務の記録。
- **曲の状態**を `予定→下書き→自己確認済→人間試聴済→承認` で持つ（`tracks.md` に列を足す）。「人間試聴済」までは「仮」。
- **やり直しは1曲2回まで**を目安にし、超えたら企画書を見直す。

## プロデューサー
- 企画書に「**避けたいこと**」欄を足す（学習メモのテンプレ10項目）。参考曲は曲名でなく「性質」を言葉で書く。
- 受け入れ基準を**企画書の段階で決める**（第1段=Claudeの自動確認、第2段=人間の耳）。人間への依頼は数曲まとめる。
- 最初に**キューリスト**（音楽が必要な場面の一覧）と**音楽バイブル**（柱3〜5・スタイルガイド・主題の一覧・避けたいこと・音量の方針）を作る。

## 構成作家
- 構成表に「緊張度（0〜5）」列、「遷移・仕掛け」欄（入り・出し・伏線）を足す。
- **主題台帳**（骨格・意味・登場する曲・変奏の種類）を作り、主題は3系統程度。**音による伏線**は伏線台帳に記録。
- 変奏は物語の意味と対応させ、1回に1〜2要素。ボス戦は最低2段構成＋1小節のスティンガー。

## 作曲家
- 手順に「4→8→16小節で拡大」「問いと答え（ピリオド／センテンス）」「強拍は和声音・非和声音は弱拍でステップ解決」「リズムの型は2〜3種類」を足す。
- **類似を避ける手順**: 最初に制約を3つ決める（調・拍子・リズム型）／動機はランダムな制約から作る／コード進行は機能和声の型だけで1か所は偽終止か転調／完成後に Parsons code と冒頭6音の確認／由来を記録。
- 1パート同時1音なので、和音はアルペジオかパート分けで書く。

## アレンジャー
- **引き算の編曲**を原則に足す（全部入りのループを先に作り、セクションごとに抜く）。セクション別の密度設計表と、ジャンル別の編成表を使う。
- 失敗の直し方（平坦・濁り・音割れ・機械的・作り物っぽい弦やブラス）を点検項目にする。

## ミキサー
- **反復のルール**: 版ごとに保存、1回に変えるのは1〜2点、直す前に問題を言葉にする、ON/OFFを音量差ゼロで比べる、休憩と別環境での確認。
- 診断に**相関係数と Mid/Side 比**を足す。ステムの**ヌルテスト**（パート別に書き出して合計し、全体と比べる）を自動化する案。
- **書き出しは2種類**: 聴く用（ピーク-1dB）と、ゲーム内の大きさを測る用（`render-catalog.mjs --raw`）。曲を足したら音量補正表を更新。
- ループ: 継ぎ目の処理（余韻を先頭に重ねる）、MP3は使わない。BGMとSEの音量帯を決め、ダッキングを検討。

## 聴取係
- 聴取依頼のテンプレ（Q1〜Q10）と**感想→直す点の変換表**を使う。人間への依頼は1回1〜3曲、質問はQ1〜Q4＋Q10を基本に。
- 自動でできる検査（両端の無音・ゼロ交差・曲間の音量差・ループ長・同時に鳴る音数・帯域の偏り）を「計測値」として報告し、聴感の判断と分ける。
- ブラウザ・スマホ・イヤホンのチェックリストと、音の不具合報告の書式。聴取メモは `tracks.md` に原文のまま残す。

## 法務
- チェックリストに、**旋律の照合（音名と音価で書き出して比較）の記録**、**素材の規約原文を `assets-src/` に保存**、**AI支援の記録（ツール名・日付・指示の要約・人間が決めた点）**、配信・動画投稿の方針（説明書に明記）を足す。
- **専門家に相談する基準**（旋律が数小節にわたり似ている／AIの学習元が不明／GPL・SA・独自規約の波及が不明／収益化の前／指摘を受けたとき）を明記。
- 日本の考え方（類似性＋依拠性、偶然の暗合は侵害でない、旋律が重視される）を前提に書く。ただし**原文は未確認**。
