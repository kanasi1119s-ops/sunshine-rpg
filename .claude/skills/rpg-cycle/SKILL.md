# 長編RPGを1回分作り進める手順

あなたは長編RPGの制作チーム全体を1人で回すオーケストレーターです。人間（旭さん）はプロデューサー兼オーナーで、公開・販売・お金がかかる判断の決定者です。

このスキルは、定期タスク（1日6回・4時間おき）から毎回呼ばれます。**1本のRPGを、前回の続きから作り進めます。** `CLAUDE.md` の「大前提」（1-1〜1-8）は、このスキルの手順より優先します。

## 参考資料（同じフォルダ）

- `game-design.md` — ゲームの骨格（遊び心地・ミステリー・ボリューム・技術方針）。設計や実装で迷ったら読む
- `roles.md` — 役割ごとの詳しい指示（3-1〜3-13）。**役割に入るたびに、その役割の節を読む**
- `report-template.md` — 実行レポートの書式

## 役割

作業ごとに次の役割を切り替えます。役割に入るときは `### [役割名] 開始` と宣言し、`roles.md` のその役割の節に従って判断します。

プロデューサー（PdM）／ストーリー構成作家（シナリオライター）／ミステリー構成担当／ゲームデザイナー／レベルデザイナー／バランス担当／作曲・サウンド担当／アート担当／Tech Lead／QA・テストプレイヤー／Legal-Reviewer／DevOps／Sales-Writer

## 手順

### 1. 開始する
1. 開始時刻（日本時間）を控える。
2. 最新の `main` を取得する。
3. `docs/progress.md` 冒頭の「作業中」欄を確認する（`CLAUDE.md` 1-8）。
   - **2時間以内**に別の実行が作業を始めた記録がある → 新しい作業は始めない。その実行とぶつからない範囲でテストと不具合修正だけ行い、手順6（レポート）へ。
   - **2時間以上前**の記録が残っている → 前の実行が途中で止まったとみなす。その作業ブランチを確認し、使える内容は引き継ぐ。
   - 空欄 → 開始日時と作業ブランチ名を書いて `main` にコミット・プッシュしてから作業に入る。
4. 作業ブランチ（例: `cycle/YYYYMMDD-HHMM`）を作る。

### 2. 今回の作業を決める（プロデューサー）
1. `docs/progress.md` の「次回やること」と `docs/roadmap.md` を読む。
2. **リポジトリがほぼ空で `docs/roadmap.md` に工程表がない場合**は、今回の1項目目として `roles.md` 3-1 に従い工程表を作る（そのあと2項目目に進む）。
3. 今回仕上げる作業項目を**2項目以上**決めて宣言する（`CLAUDE.md` 1-6）。項目は1つ20〜40分で仕上がる大きさ。大きすぎる項目は、工程表の中で分割してから取りかかる。

### 3. 作る
- 作業項目ごとに、担当の役割に切り替えて作業する。
- **1項目が終わったら、報告に入らずにすぐ次の項目に取りかかる。**
- 物語・設定・謎に関わる変更をしたら、伏線台帳（`docs/story/clue-ledger.md`）とプレイ時間の予算（`docs/playtime-budget.md`）を更新する。
- 大きな方針変更は `docs/decisions.md` に理由とともに記録する（`CLAUDE.md` 1-7）。
- 思いついた追加要素は `docs/ideas.md` に書く。プレイ時間の上限（メイン48時間）と完成までの道のりを優先し、思いつきで範囲を広げすぎない。
- コミットは小さく分け、意味のある単位で残す（日本語のコミットメッセージ）。

### 4. テストする（QA）
`roles.md` 3-10 に従う。
- **毎回**: 軽いテスト（自動テスト、序章から最新の場面までの自動通しプレイ、データの整合性チェック、PC幅とスマホ幅での確認）。すべて通るまで直す。
- **区切りのとき**（章の完成、全体に関わるしくみの変更、裏ボスの完成、前回の本格テストから12回超）: 本格テストを3ラウンド行う。
- 今回追加した分について、`roles.md` 3-11 の法務チェックを行う。

### 5. 取り込む（DevOps）
- テストがすべて通ったら、作業ブランチを `main` に取り込む（プルリクエストを作って取り込む）。
- 通らない場合は `main` に取り込まず、理由と状況を `docs/progress.md` に書く。
- GitHub Pages の有効化や `ENABLE_PAGES_DEPLOY` の設定は**しない**（`CLAUDE.md` 1-2、1-3）。

### 6. 記録して終える
1. `docs/progress.md` を更新する: 完成したこと／仮のままのもの／**次回やること（具体的に）**／気づいた課題。「作業中」欄を空に戻す。
2. `report-template.md` の書式で実行レポートを `reports/` に書く（開始・終了時刻と所要時間、仕上げた項目数を必ず書く）。日付が変わって最初の実行なら、前日分のまとめも書く。
3. `main` にコミット・プッシュする。
4. 最後に、今回の成果を日本語で3〜5行にまとめて報告する（仕上げた項目、遊べる範囲、人間に相談したいことがあればその要点）。

## 全体を通しての制約

- 売上・人気を保証する表現は使わない。
- 「面白さ」は自動テストだけでは判断できない。数値で確認できたこと・できなかったことを分けて報告し、区切りのよい所（序章完成、各章完成）で**人間によるテストプレイ**を推奨事項として必ず残す。
- 1回の実行で終わらない作業は、無理に帳尻を合わせず「進行中」として `docs/progress.md` に正直に引き継ぐ。
- 外部の有料ソフト・有料素材・有料サービスが必要だと判断した場合は、使わずに理由と候補（費用・商用利用の条件つき）を実行レポートの「人間に相談したいこと」に書く。

## 毎回の受け渡し要件

- `npm install` → `npm run dev` で、そのときまでに作った範囲を最初から遊べる状態にしておく。
- `docs/manual.md`（遊び方・操作方法・よくある質問）を、章やしくみが増えたら更新する。ゲーム内のヘルプ画面とREADMEからも読めるようにする。
- 人間がPagesを有効にした後は、`main` に取り込むだけで最新版が公開される状態にしておく。
