# 役割別の詳細指示

このファイルは `rpg-cycle` スキルの参考資料です。役割に入るときは、その役割の節を読んでから作業してください。

文中の番号の参照先: 「1-x」は `CLAUDE.md` の「大前提」、「2-x」は同じフォルダの `game-design.md`、「3-x」はこのファイルです。

## 3-1. プロデューサー（PdM）
**最初の実行（リポジトリがまだ空のとき）にやること**
- `docs/roadmap.md` に全体の工程表を作る。目安は次の通り（順番は変えてよいが、「早い段階で最初から最後まで1本の道が通る」ことを重視する）:
  1. **基盤**: エンジン、マップ表示、歩行、会話、戦闘、セーブ、BGM再生、デバッグメニュー
  2. **物語の設計書**: 世界観・全章のあらすじ・謎の真相・伏線台帳・主要キャラクター（3-2、3-3）
  3. **序章を遊べる形にする**（町1つ・ダンジョン1つ・ボス1体・曲数曲）＝見本となる完成品
  4. **第1章〜終章を1章ずつ**（各章を「地図 → イベント → 敵とバランス → 曲 → テスト」の順に）
  5. **サブストーリー**（各章に合わせて順次）
  6. **クリア後ダンジョンと裏ボス**
  7. **仕上げ**（全体の通しプレイ、バランス再調整、会話の推敲、演出強化）
- 工程の各段階を、**1つあたり20〜40分で仕上がる作業項目**に分けてチェックリストにする（1回の実行で2項目以上進める前提。1-6参照）
**毎回の実行でやること**
- `docs/progress.md` と `docs/roadmap.md` を読み、今回やる作業項目（2項目以上）を決めて宣言する
- プレイ時間の予算（`docs/playtime-budget.md`）を確認し、超えそうなら削る判断をする
- 実行の最後に `docs/progress.md` を更新する（完成したこと／仮のままのもの／次回やること／気づいた課題）

## 3-2. ストーリー構成作家（シナリオライター）
**設計段階で作るもの（`docs/story/`）**
- `bible.md`: 世界観の設定書（世界の成り立ち、国と地方、歴史、魔法や技術のしくみ、宗教・文化、通貨、地理）
- `characters.md`: 主人公・仲間（4〜6人）・主要な敵役・黒幕・重要NPC。一人ひとりに「目的」「秘密」「成長の筋道」「口調の特徴とセリフ例」を書く
- `structure.md`: 物語全体の構成。序章〜終章それぞれについて、舞台、事件、起承転結、その章で明かされる真相、仲間の出入り、章の最後の引き（次が気になる終わり方）、予定プレイ時間
- `side-stories.md`: サブストーリーの一覧（発生条件、あらすじ、報酬、本編や裏ボスとのつながり、予定時間）
- `secret-boss.md`: 裏ボスの物語上の正体、クリア後ダンジョンの構成、そこへ導く伏線（本編・サブストーリーのどこに置くか）
**会話・文章の書き方**
- 各キャラクターの口調を一貫させる。子どもからお年寄りまで読める自然な日本語で書く
- 説明ばかりにならないよう、会話のやりとりで世界や人物を見せる
- 笑い・切なさ・緊張の場面を章ごとにバランスよく入れる
- 町の人のセリフは、章の進行・事件の前後で変える（2-2）
- 1つの場面で長く話しすぎない。大事な情報は手帳に自動記録して、読み逃しても困らないようにする
**Exit基準（設計段階）**: 全章のあらすじが最後まで書かれ、各章の予定時間の合計がメイン48時間以内に収まっていること。ミステリー構成担当が伏線台帳でチェック済みであること。

## 3-3. ミステリー構成担当
- `docs/story/mystery.md`（**真相の設計書**）: 物語全体の謎、黒幕とその動機、隠された真相、各章の事件の真相と犯人・トリック・動機
- `docs/story/clue-ledger.md`（**伏線台帳**）: 伏線・手がかり1つにつき1行で管理する表
  | ID | 内容 | 仕込む場所（章・マップ・イベント） | 回収する場所 | 種類（手がかり／伏線／レッドヘリング） | 実装状況 |
- 推理パートの問題を作る（問い、選択肢、正解、根拠となる手がかりID）
- **フェアさのチェック:** 各推理パート・真相の説明について、根拠となる手がかりがすべてそれより前に入手できるかを伏線台帳で確認する（自動テストでも確認する。3-10）
- 章を作るたびに伏線台帳を更新し、「仕込んだが回収していない伏線」「回収したが仕込んでいない真相」をなくす

## 3-4. ゲームデザイナー
- `docs/design/`: 戦闘ルール（ダメージ計算式、命中・会心・素早さによる行動順、状態異常、属性）、成長（経験値曲線、能力の伸び）、呪文・特技の体系、装備の体系、職業または仲間モンスターのしくみ、乗り物、全滅時の扱い、依頼（クエスト）の評価と報酬、推理パートの評価と報酬
- 呪文・特技・アイテム・敵の名前は、すべてオリジナルで世界観に合ったものにする（1-1）
- 数値はすべてデータファイルで調整できるようにする

## 3-5. レベルデザイナー
- 町: 施設（宿屋・武器屋・防具屋・道具屋・依頼を受ける所・教会に当たる場所など）の配置、住人の配置と生活感、章ごとの変化
- フィールド: 行ける範囲の広がり方、迷いすぎない道しるべ、寄り道のごほうび（宝箱・隠し場所）
- ダンジョン: 1つごとに見どころのギミック（スイッチ、暗闇、一方通行、仕掛け扉、謎解きなど）を1つ以上。長すぎるダンジョンには途中の回復・記録ポイントを置く
- 地図データはタイルマップ形式（例: Tiled の JSON 形式）で作る

## 3-6. バランス担当
- 章ごとの「想定レベル」「想定の装備」「所持金の目安」を決め、ボス戦を自動シミュレーションで検証する（想定レベル・想定装備で勝率70〜90%、想定より3レベル低いと苦戦、など）
- 裏ボスは、全員が最大付近のレベル＋最強クラスの装備＋作戦がそろって勝率50%前後を目安にする
- `docs/playtime-budget.md` を、章の内容が増えた回ごとに更新する（2-3の見積もりルール）

## 3-7. 作曲・サウンド担当（BGM・効果音）
**方針: 外部ソフトなしで、ゲームの中で音を作って鳴らす**
- BGMは、ブラウザの音声機能（Web Audio API）を使った**ファミコン〜スーパーファミコン風の音源**で鳴らす。曲は楽譜データ（音の高さ・長さ・音色・テンポなどを書いたデータファイル）として作曲し、リポジトリに置く。音声ファイルを外から持ってくる必要はない
- 作曲するときは、メロディ・和音・リズムを**すべてオリジナル**で作る。既存のゲーム音楽・既存曲のメロディやコード進行をなぞらない（1-1）。**特定の実在の作曲家・アーティストの作風を狙って似せることもしない**（名前を挙げられても同様。曲調の系統〈チップチューン、オーケストラ風など〉を参考にするのはよい）
- **サウンドの方向性: 「16bit風チップチューン」×「現代的な音づくり」のハイブリッド。**
  - 基本の音色・アルペジオ・パルス波のリードなどはスーパーファミコン世代の質感（16bit風）を土台にする
  - そこに、現代のゲーム音楽的な工夫を重ねる: 単純な三和音だけでなく**7th・9thなどのテンションを含む和音**、**転調・非機能和声（意外性のある進行）**、**ドローンやパッドを重ねた広がりのある響き**、**曲中でのテンポ・拍子の変化**、**ダイナミクス（静かな部分と盛り上がる部分の差）**を意識する
  - Web Audio APIの音源（波形合成・簡易FM・ノイズなど）の組み合わせ方を工夫し、チップチューンの質感を保ったまま「懐かしいだけ」で終わらない曲にする
  - **場面ごとの雰囲気の強め方（旭さんの好み）:**
    - 悲しい・切ない場面の曲は、現代音楽的な**不協和音（不安定な響きの和音・音のぶつかり）**を強めに使う
    - 戦闘曲は**疾走感**を強めに（速いテンポ、細かい音の刻み、前のめりなリズム）
  - 曲ごとにこの方針をどう反映したか一言メモを `docs/sound/tracks.md` に残す
- 必要な曲（最低限。章が増えたら追加）:
  - タイトル、オープニング、エンディング、スタッフロール
  - 町（明るい町、港町、寂れた町など3曲以上）、城、村
  - フィールド（序盤、船、空の乗り物、終盤の4曲以上）
  - ダンジョン（洞窟、塔、遺跡、最終ダンジョン、クリア後ダンジョン）
  - 通常戦闘、ボス戦、ラスボス戦、**裏ボス戦**
  - **調査・推理のテーマ**（ミステリー場面用）、真相が明かされる場面、緊迫、悲しみ、ほのぼの、宿屋（短いジングル）、レベルアップ（ジングル）、全滅、勝利ファンファーレ
- 主人公たちのテーマ・黒幕のテーマなど、**繰り返し出てくる旋律（ライトモチーフ）**を決め、アレンジを変えて章の要所で使う
- 各曲はループ再生できるように作り、ループのつなぎ目で音が途切れないようにする
- 効果音（決定・キャンセル・カーソル・攻撃・呪文・回復・宝箱・扉・階段・ダメージ・会心など）も同じ音源で作る
- 音量設定（BGM・効果音を別々に）と、消音を付ける。スマホではタップするまで音が鳴らないブラウザの決まりに合わせる
- `docs/sound/tracks.md` に曲の一覧（曲名・使う場面・テンポ・調・ライトモチーフ・状態（仮／完成））を記録する
- **外部の音楽ソフトやサービスが必要だと判断した場合**は、使わずに理由と候補を実行レポートの「人間に相談したいこと」に書く（費用・商用利用の条件を必ず添える）

## 3-8. アート担当（ドット絵）
- **ドット絵を作る・作り直すときは、必ずドット絵エディタ（Artifact: https://claude.ai/artifact/Xo7VKZU9cHJk15BnvVmxdp ）を使う**（2026-09-29決定）。エディタで描いて見た目を確かめ、書き出した色番号データ＋パレットを `portraits.ts`・`monsters.ts`・`tile-art.ts` などのデータに反映する。想像だけでASCIIグリッドを書かない。エディタでの確認結果（どのキャラ・モンスターをいつ作ったか）は実行レポートに書く。エディタで扱えない事情（環境で開けない等）があるときは、その理由をレポートに正直に書き、仮のドット絵として扱う
- キャラクター・敵・マップタイル・アイコン・画面の枠は、**自作のドット絵**を基本とする。ドット絵は、色番号を並べたデータ（パレット＋ドットの並び）としてリポジトリに置き、プログラムで画像にする方式でもよい
- 方向性は「ドット絵×奥行きのある光の演出」（既存作のHD-2D技法そのものはまねない）。そのうえで、**ドット絵自体のクオリティ（解像度・書き込み量・パレット数）を高めに取る**ことを優先する（2026-09-28決定、`docs/decisions.md`参照）。単色プレースホルダーのままにせず、章の区切りごとに本番品質へ引き上げていく
- 外部素材を使う場合は、CC0など**商用利用可能で出典表示の条件を満たせるもの**に限り、`CREDITS.md` に出典・ライセンス・URLを記録する
- 既存作のキャラクター・モンスターに似たデザインにしない（1-1）
- 敵は、同じ絵の色違い（上位種）を使ってよいが、各地方に新しい見た目の敵を必ず入れる
- 文字は読みやすい日本語フォント（商用利用可のもの）を使い、ライセンスを `CREDITS.md` に記録する

- 2-4の技術方針に従って実装する
- ゲームの中身（ロジック）と画面表示を分け、中身だけをテストや自動プレイで動かせるようにする

## 3-10. QA / テストプレイヤー
テストは「毎回の軽いテスト」と「区切りでの本格テスト（3ラウンド）」の2段階で行う。

**A. 毎回の実行で行う軽いテスト（作業項目を `main` に取り込む前に必ず）**
- 自動テスト（戦闘計算・成長・アイテム・セーブと読み込み）がすべて通る
- 自動通しプレイで、序章から現在の最新の場面まで進行不能がない
- データの整合性チェック（会話・イベントが参照するフラグ・アイテム・マップ・曲がすべて存在する）
- 今回作った部分を、PC幅とスマホ幅で一度ずつ動かして確認する
問題があれば直してから取り込む。直せない場合は取り込まず、`docs/progress.md` に書く。

**B. 区切りでの本格テスト（3ラウンド）** — 次のどれかに当てはまる実行で行う
- 1つの章（または序章・終章）が完成したとき
- 戦闘・成長・セーブなど、ゲーム全体に関わるしくみを変えたとき
- クリア後ダンジョン・裏ボスが完成したとき
- 前回の本格テストから、実行回数が12回（約2日分）を超えたとき

本格テストでは、1回ごとに問題を洗い出して直し、直したあとにもう一度テストする。
```
Round 1: テスト → 問題点リスト化 → 修正
Round 2: 再テスト（Round 1 の修正確認＋新しい問題の発見） → 修正
Round 3: 再テスト（Round 2 の修正確認＋前の章が壊れていないかの確認） → 修正 → 最終判定
```
**本格テストの各ラウンドで確認すること**
- **自動テスト**: 戦闘計算、成長、アイテム、セーブと読み込み（古いバージョンのセーブを含む）
- **自動通しプレイ**: 自動で操作するプログラムで、序章から今回作った章の最後まで通して、**進行不能（詰み）がないこと**を確認する（必要なフラグがすべて立つ、行き止まりがない、出られない場所がない）
- **データの整合性チェック**: 会話・イベントが参照するフラグ・アイテム・マップ・曲がすべて存在すること
- **ミステリーのフェアさチェック**: 推理パートと真相の説明で使う手がかりが、すべてそれより前に入手できること（伏線台帳と照合）
- **バランス検証**: ボス戦の自動シミュレーション（3-6の基準）
- **画面・操作の確認**: PC幅とスマホ幅の両方で、文字がはみ出さない、ボタンが押せる、音が鳴る
- **会話文の確認**: 誤字脱字、口調のぶれ、名前の表記ゆれ
- 結果は `docs/debug-log.md` に「日付 / ラウンド / 見つけた問題 / 重大度 / 直した内容 / 確認結果」の表で記録する
**Exit基準**: 毎回の軽いテストがすべて通っていること。本格テストを行った回は、3ラウンドを終え、重大な不具合（止まる、進めなくなる、セーブが壊れる、勝敗や報酬の誤り）がゼロであること。軽い課題は一覧にして次回へ持ち越してよい。

## 3-11. Legal-Reviewer（毎回、今回追加した分について）
- [ ] 名前（作品名・キャラ・地名・呪文・モンスター・アイテム）が既存作品と同じ、またはまぎらわしくないか
- [ ] ストーリー・設定・セリフが既存作品のまねになっていないか
- [ ] 曲のメロディ・和音進行が既存曲に似すぎていないか（作曲担当に確認し、疑わしい曲は作り直す）
- [ ] ドット絵が既存作のキャラクター・モンスターに似すぎていないか
- [ ] 外部素材・フォントのライセンスが商用利用可能で、`CREDITS.md` に記録されているか
- [ ] タイトルが既存の商品名とまぎらわしくないか（商標の最終確認は人間が行う旨を実行レポートに書く）
- [ ] 対象年齢に合わない表現（過度な暴力・差別的表現など）がないか
- [ ] リポジトリに秘密情報・個人情報が含まれていないか
**Exit基準**: すべて確認済み、または「要対応」として具体的に書かれていること。

## 3-12. DevOps（公開準備。公開スイッチは入れない）
- ビルドとテストが通ることを確認する
- `.github/workflows/deploy-pages.yml` を作る（最初の実行で作り、以後は保守する）:
  - トリガー: `main` への `push`、`pull_request`、手動実行
  - build ジョブ（常に実行）: 依存関係インストール → テスト → ビルド → Pages用アーティファクトのアップロード
  - deploy ジョブ: `if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request' && vars.ENABLE_PAGES_DEPLOY == 'true'` のときだけ実行。`actions/deploy-pages`、`environment: github-pages`、権限は `contents: read` / `pages: write` / `id-token: write`、`concurrency` で同時実行を防ぐ
  - `enablement: true` は指定しない。各アクションのバージョンは公式ドキュメントで最新を確認する
- `docs/release-guide.md`（日本語）に、人間がPagesを有効にする手順（Settings → Pages の Source を「GitHub Actions」、変数 `ENABLE_PAGES_DEPLOY=true` の追加、公開の止め方）を書く
- **作業ブランチの扱い:** 作業ブランチで作業し、テストがすべて通ったら `main` に取り込む（プルリクエストを作って取り込む）。次の実行は必ず最新の `main` から始める。テストが通らない場合は `main` に取り込まず、その理由を `docs/progress.md` に書く

## 3-13. Sales-Writer
- 序章が遊べる形になった時点で、紹介文（キャッチコピー、30秒で分かる紹介、特徴3点、遊べる範囲、推定プレイ時間）を `docs/sales-copy.md` に作る。以後、章が増えるたびに更新する
- サンシャインソフトウェアのサイト（https://kanasi1119s-ops.github.io/）に掲載するための紹介ページ用の文章も用意する（掲載作業そのものは人間の承認後）
- 誇大表現・根拠のない断定を使わない
